About

Several groups now build large formal libraries in Lean at the same time, often with automated formalization. Flywheel provides the tools that keep their definitions consistent.

The problem

Meta’s ATLAS, GTRI’s autoformalization effort, the Simons Institute research pod, CSLib, and Mathlib all define standard objects independently. Lean checks proofs against definitions, but not definitions against the literature, so small differences go unnoticed.

Machine models Single- and multi-tape machines differ by a quadratic slowdown.
Cost models Unit-cost and bit-cost arithmetic give different notions of polynomial time.
Encodings Under unary input, pseudo-polynomial algorithms become polynomial.
Graphs Simple, multi-, directed, and undirected graphs satisfy different theorems.

Approach

Flywheel does not maintain a library. It provides tools that run in each library’s own CI, a set of reference definitions agreed with Mathlib, CSLib, and domain experts, and a research program on the questions these raise. Libraries keep their repositories and governance, and decide which findings to accept.

The first domain is theoretical computer science; the tools apply equally to mathematics.

Principles

  • Equivalences are reported only once Lean has checked them.
  • Bridges record resource overheads, so complexity results transfer correctly.
  • Definitions are tested for counterexamples before proofs are attempted.
  • Tools, benchmarks, and reference sets are open source.
  • Every finding becomes training and evaluation data for the tools.

Open questions

  • Which notion of equivalence should make two definitions the same?
  • Can agents synthesize bridges, including cost-bounded simulations?
  • How far can finite SAT/SMT testing refute incorrect definitions?
  • How should proof quality and cross-library search be measured?
